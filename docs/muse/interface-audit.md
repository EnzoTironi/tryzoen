# Muse interface audit

Observed on 2026-09-27 in the user's signed-in Muse account in Chrome, on desktop and at a 425 × 719 mobile viewport. The user also supplied six App Store screenshots and five screenshots of the mobile web interface, two desktop agent-panel screenshots a fullscreen SOUL.md editor reference, and two mobile goal-detail/action-sheet references. This is the reference inventory for the universal companion, alongside [architecture and release gates](universal-client.md).

**The existing companion is not at feature or visual parity.** In particular, Feed is not merely a list of scheduled results, Ideas is not merely a starter catalog, and tapping the avatar opens agent status rather than settings. Build the complete interactions described here, not just navigation destinations.

## Evidence and limits

- **Observed:** opened the screen, menu, or form in Chrome and inspected its controls. This does not mean destructive actions, purchases, external account linking, or every possible state were exercised.
- **Reference:** present in a user-supplied screenshot, but not reproduced in the inspected web account.
- **Reported:** described by Muse in a separate product-audit conversation that the user authorized. Treat these claims as leads, not verified implementation contracts.
- **Unverified:** inaccessible, account/platform-dependent, or not exercised safely during this audit.

No payments, new account connections, credential changes, permission changes, deletions, or messages to third parties were performed. Two questions were sent to Muse about its own product behavior. Existing personal conversation content, credentials, account addresses, document contents, and private screenshots are excluded from this repository and PR evidence.

The web creation viewer opened, but further inspection encountered an extension access error for an embedded document. Its outer controls were visible; its complete embedded behavior is unverified. The expanded emoji picker also stalled inspection. Native device, onboarding, checkout, active approval, and account-gated states cannot be established from this signed-in web account alone.

## What Muse reported, requiring verification

The authorized audit conversation described main/side-chat ownership, scheduled results returning to their originating conversation, direct file editors for identity/memory, and conversational avatar/name changes. Those align with portions of the observed UI. The following additional claims are **not verified contracts**:

- Feed generation follows a system-controlled schedule; reaction/discussion feedback changes personalization. An edited brief may trigger a new post.
- Goal nesting is limited to one level; goals have completed/active states and dated progress. Background monitoring requires actual scheduled work.
- Schedule editing may stage a chat draft; pause/resume may be conversational. Availability differs by platform and task ownership.
- Voice notes, native dictation, OS share extensions, Mac quick chat and default-assistant behavior are platform-dependent. An absent web microphone does not establish absent native voice.
- Sharing creates public links; static pages and stateful interactive apps have different publishing capabilities. This must be verified before shipping publication controls.
- Attachment limits, conversion behavior, retention periods and native viewer support differ by surface. Do not copy the assistant's numeric claims into validation rules.

Muse could not initially explain the visible Heartbeat label. The UI confirms its cadence and history, but the exact relation between Heartbeat, Feed generation, proactive messages and goal-owned jobs remains unresolved. Do not combine these concepts based on a guess.

## Implementation order and ownership

1. **Navigation and status:** use `packages/companion-ui` for adaptive shells, shared sheets/panels and accessible controls; retain `app/companion` and `apps/mobile` as platform adapters. Preserve native five-tab versus web six-item differences. Add the four-tab status surface without taking over settings navigation.
2. **Conversation completeness:** compose the existing shared session controller with message actions, quoted context, real attachments, durable approvals, browser preview and artifact parts. Eve remains the owner of tool execution and approval responses. Extend owning message/event contracts rather than mirroring them with UI-only schemas.
3. **Durable product records:** give goals detail/history/subgoals an explicit owner; distinguish monitoring from milestones. Build personalized Ideas and editorial Feed with source/rationale, feedback, bounded pagination and isolated per-account generation. Preserve scheduled results as execution history, not the sole Feed definition.
4. **Settings and integrations:** expose existing account/provider/permission services through complete shared screens. Search Eve's registry before adding each missing integration, following `docs/recipe-integrations/README.md`. Keep unsupported providers out of connected/available production lists until their flow actually works.
5. **Artifacts and devices:** reuse file storage/editor owners; add previews, selection, publishing and permission boundaries. Implement voice, notifications, pairing and OS access in explicit adapters. Device and payment operations need working services, not enabled-looking buttons.
6. **Acceptance:** verify each row's happy, empty, loading, error, denied and revoked-access states as applicable. Use synthetic data for screenshots/video and upload via `gh --attach`. Run the required checks/build and native device validation before releasing.

## Attachment implementation checkpoint — 2026-09-27

The shared composer accepts files through explicit browser/Electron and Expo adapters. Web and native use the same validated message composition.
